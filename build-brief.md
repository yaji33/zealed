# Build Brief: Confidential Prize Savings (Zama Season 4 Bounty)

Project codename: Zealed

## 1. Thesis

A confidential, no-loss prize savings protocol. Users deposit into a shared pool, yield is distributed via periodic prize draws, principal stays withdrawable at any time. Deposits, balances, and individual winnings are encrypted end-to-end using the Zama Protocol (fhEVM). Winner selection is provably fair and publicly verifiable without exposing any individual's position.

Differentiator: today's PoolTogether makes savings behavior a public spectacle (deposit size, odds, wins). This punishes exactly the users (privacy-conscious individuals, companies, DAOs) it should be attracting. Confidentiality here is not a checkbox, it is the feature that unlocks a user segment the public version structurally excludes.

## 5. Smart Contract Architecture

### ConfidentialVault.sol
- Holds cUSDC deposits
- Tracks each user's encrypted balance (`euint64`) and an encrypted time-weighted average balance (TWAB) for fair ticket weighting
- `deposit(einput amount, bytes proof)` — encrypted amount in, balance updated homomorphically
- `withdraw(einput amount, bytes proof)` — principal withdrawable anytime, no lockup. This is a hard bounty requirement, do not gate it behind draw cycles.
- Emits only non-sensitive events (deposit occurred, withdrawal occurred) — no amounts in plaintext events

### TicketEngine.sol
- Converts each user's encrypted TWAB into an encrypted ticket weight for the current draw period
- Maintains an encrypted running cumulative offset per user (their "slice" of the total ticket range), NOT computed in a single loop at draw time — updated incrementally as deposits/withdrawals happen, so draw time has no O(n) cost

### DrawManager.sol — the core design decision

Do NOT implement winner selection as "loop over all depositors and homomorphically compare." At any realistic N this is gas-prohibitive and slow with fhEVM's async decryption oracle, and it will look fragile in a security review — exactly the opposite of what "production-ready" judging wants to see.

Instead, use a **pull-based, per-user verification pattern**:

1. At draw time, a public verifiable random value `r` (0 to totalTickets) is finalized via commit-reveal (commit block hash ahead of time, reveal after, standard pattern — avoidable manipulation window).
2. `r` is plaintext and public. This is fine: `r` alone reveals nothing about any individual's balance or weight.
3. Each user calls `checkIfWon()` themselves, anytime after the draw. The contract does exactly ONE encrypted comparison: is `r` within this caller's encrypted [start, start+weight) range? Result is an encrypted bool.
4. If true, an encrypted prize amount is credited to that user, claimable via the standard Zama user-decrypt flow.
5. Total protocol-side compute is O(1) per claim, paid by the claimant. No one call does unbounded work. This is the answer to "how do we make FHE winner selection scale" and it's also the more honest, verifiable design: anyone can audit that `r` was generated fairly, even though they can't see who it belonged to.

### PrizeClaim (can live inside DrawManager)
- Standard Zama user-decrypt / EIP-712 reencryption pattern
- Winner decrypts their own prize client-side, protocol never reveals amount to anyone else

## 6. Draw Flow (sequence)

1. Draw period closes (e.g. weekly)
2. Commit phase: commit to a future block number as the randomness source
3. Reveal phase: derive `r` from that block's hash, finalize publicly
4. Claim window opens: any user can call `checkIfWon()` — pull, not push
5. Winners see an encrypted prize credited to their address, decrypt client-side, claim

## 7. Withdrawal Flow

- Independent of draw cycle entirely
- `withdraw()` reduces encrypted balance and TWAB immediately
- No lockups, no cooldowns — this is both a bounty requirement and the actual product promise ("no-loss")

## 8. Frontend Spec

Two views, sharing one design system (carry over your existing near-black / gold-accent / monospace numerals system from Bantam if it fits the tone — otherwise a clean dark neutral with one confidential-signal accent color):

**Public view** (no wallet required)
- Aggregate TVL, total yield generated, total prizes paid to date
- Draw history: draw number, timestamp, whether it settled — no individual data
- This is the "everything else is visible, only positions are hidden" proof point — make it visually obvious what's public vs private

**Private dashboard** (wallet-gated)
- Connected wallet's decrypted balance, TWAB, current ticket weight
- Draw result for this user (won / didn't win), decrypted prize if applicable
- Deposit / withdraw actions
- Optional: "Reveal that I won" toggle (see Section 9) — off by default

## 9. Ship-if-time: Selective Disclosure (the differentiator, kept small)

Do not build a general ZK selective-disclosure system. Build exactly one thing:

- After claiming a prize, the winner can optionally call `revealWin()` which publishes "address X won tier Y this draw" without amount
- This is cheap (one flag flip, no new crypto primitive) and is the single clearest demo moment for your thesis: "everything is private by default, but the user controls what to reveal." Use this in the video.

## 13. Security Notes (given the audit incentive)

Zama has stated the strongest submission may get a professional OpenZeppelin audit and further development support. Build like that's real:

- No plaintext amounts in events or logs, anywhere
- Reentrancy guards on deposit/withdraw/claim
- Commit-reveal randomness must not be manipulable by whoever controls the committed block (standard front-running/withholding checks)
- Write tests for the pull-based checkIfWon path specifically — this is the novel part of your architecture and the part most likely to have an edge case
